# PaintWeb — протокол клиент ↔ TouchDesigner

Версия: **1**. Этот файл — контракт. Клиент и TD-рантайм обязаны совпадать с ним
байт-в-байт, иначе рисование «поедет».

```
┌─────────────────────┐        HTTP  /  WS (один порт, по умолчанию 9980)
│ планшет / телефон   │  ────────────────────────────────────────────►  ┌──────────────────┐
│ браузер = тонкий    │  ◄────────────────────────────────────────────  │ TouchDesigner    │
│ клиент + превью     │   состояние, патчи PNG, прокси JPEG             │ = авторитет      │
└─────────────────────┘                                                 └──────────────────┘
```

## 0. Разделение ответственности

- **TD владеет пикселями.** Слои, буферы кисти, undo, композит, вывод — всё в TD.
- **Клиент владеет своим экраном.** Pan/zoom, отрисовка превью, панели, ввод.
- **Оптимистичное превью.** Клиент рисует мазок локально сразу (нулевая задержка), но
  его результат **временный**: как только приходит патч от TD, соответствующая
  область **полностью заменяется** серверными пикселями. Расхождение обязано
  исчезать, а не накапливаться.
- **Сервер — единственный источник истины.** Клиент никогда не «дорисовывает»
  то, что не подтвердил сервер, кроме текущего активного мазка.

## 1. Полотно

- Полотно задаётся сервером: `canvas.w × canvas.h` (по умолчанию 1920×1080).
- Все координаты в протоколе — **в пикселях полотна**, целые числа.
- Точки мазка на клиенте — **нормализованные 0..1** (см. §4), сервер умножает на размер полотна.
- Кисть задаётся размером **в пикселях полотна**, а не в пикселях экрана. Значит,
  рисуя с телефона, ты получаешь ту же толщину, что и на большом полотне.

## 2. HTTP

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/` , `/index.html` | страница рисовалки |
| GET | `/app.js` , `/style.css` | статика |
| GET | `/api/state` | полное состояние в JSON (то же, что `welcome`): резерв и отладка |
| GET | `/api/sources` | список доступных входных файлов: `{"list":[{"name","path","type"}]}`, `type` = `image` \| `video` |
| POST | `/api/upload?name=foo.png` | тело = сырые байты файла, сохраняется в `paint/uploads/`, ответ `{"ok":true,"name":"foo.png","path":"..."}` |

Ответы `text/html`, `text/javascript`, `text/css`, `application/json` — с правильным
`content-type`, иначе браузер не выполнит скрипт.

## 3. WebSocket

URL: `ws://<host>:<port>/ws` (при включённой авторизации — `?token=<token>`).

**Текстовые** сообщения — JSON, поле `t` = тип. **Бинарные** — только две вещи:
точки мазка (клиент → TD) и картинки (TD → клиент). Бинарный кадр TD **всегда**
идёт сразу после текстового заголовка, описывающего его (порядок в WS сохраняется).

### 3.1 Клиент → TD

```json
{"t":"hello","w":1280,"h":800,"dpr":2,"ua":"..."}
{"t":"tool","tool":{"tool":"brush","color":"#ff3366","size":40,"hardness":0.7,"flow":0.9,"spacing":0.15}}
{"t":"layer","op":"prop","id":1,"prop":"mode","value":"mask"}
{"t":"layer","op":"prop","id":1,"prop":"visible","value":1}
{"t":"layer","op":"prop","id":1,"prop":"opacity","value":0.6}
{"t":"src","path":"paint/uploads/foo.mp4"}
{"t":"clear","layer":1}
{"t":"undo"} / {"t":"redo"}
{"t":"ping","ts":1234567}
```

`tool.tool` ∈ `brush` \| `eraser` \| `pan`. `pan` — чисто клиентский инструмент,
на сервер уходит только для синхронизации UI между устройствами.
Поле `tool` в сообщении `tool` — **частичное**: сервер мержит и рассылает полное состояние.

### 3.2 TD → клиент

```json
{"t":"welcome","ver":1,"canvas":{"w":1920,"h":1080},"layers":[...],"tool":{...},"patchHz":30,"proxyFps":2,"history":{"undo":0,"redo":0}}
{"t":"layer","op":"prop","id":1,"layer":{...}}
{"t":"tool","tool":{...}}
{"t":"patch","layer":1,"x":120,"y":80,"w":180,"h":160,"seq":17,"final":0}
{"t":"sync","layer":1,"seq":18,"w":1920,"h":1080}
{"t":"proxy","kind":"poster","seq":3,"w":960,"h":540}
{"t":"sources","list":[{"name":"clip.mp4","path":"...","type":"video"}]}
{"t":"history","undo":3,"redo":0}
{"t":"pong","ts":1234567}
{"t":"error","msg":"..."}
```

- После `patch` / `sync` / `proxy` сразу идёт бинарный кадр: PNG (RGBA, без потерь) для
  `patch`/`sync`, JPEG (без альфы) для `proxy`.
- `patch` — прямоугольник **уже готовых серверных пикселей слоя**. Клиент обязан
  сделать `clearRect(x,y,w,h)` и затем нарисовать патч поверх: альфа патча значима.
- `sync` — полный слой целиком, приходит при подключении и по запросу.
- `proxy` — изображение источника, **уже вписанное в пропорции полотна** (клиент
  просто растягивает его на весь слой источника, никакой арифметики с аспектом).
  `kind":"poster"` — статичный кадр (для картинки или первый кадр видео),
  `kind":"live"` — обновляемый прокси для видео (частота `proxyFps`, 0 = только постер).
- `final":1` в `patch` — последний патч мазка: клиент может убрать оверлей превью.

### 3.3 Слои

```json
{"id":0,"name":"Source","kind":"source","visible":1,"opacity":1,
 "srcType":"video","srcName":"clip.mp4","srcPath":"paint/uploads/clip.mp4"}
{"id":1,"name":"Paint","kind":"paint","visible":1,"opacity":1,"mode":"paint"}
```

- `mode` ∈ `paint` (рисуем поверх источника) \| `mask` (рисуем альфу источника).
- В v1 слоёв ровно два; в v2+ список расширяется, `id` остаётся ключом.
- Клиент обязан корректно работать с любым количеством слоёв в списке, рисуя
  активный (`tool.target`), но раскладку композита v1 определяет по `kind`.

### 3.4 Композит (что клиент показывает)

Для каждого слоя снизу вверх, с учётом `visible` и `opacity`:

1. `kind:"source"` → картинка из прокси-кадра.
2. `kind:"paint"`:
   - `mode:"paint"` → слой рисуется поверх **обычным `source-over`** (у пикселей есть цвет и альфа);
   - `mode:"mask"` → слой **не рисуется сам**, а служит альфой для источника: источник
     копируется во временный канвас, к нему применяется `destination-in` этой маской,
     результат рисуется на экран.

**Важно (уточнено v1).** Маска собирается как **объединение** постоянного слоя краски и
оверлея текущего мазка (альфы складываются в отдельный буфер), и только потом к
источнику применяется **один** `destination-in`. Буквальная последовательность
`destination-in` сначала слоем, а потом оверлеем неверна: вне активного мазка оверлей
прозрачен, и второй `destination-in` обнулил бы результат целиком. По той же причине
источник, над которым есть видимый слой `mode:"mask"`, не рисуется на экран «как есть» —
иначе он перекрыл бы собственную маску.

Пустой источник → шахматный фон. Композит считать не каждый кадр, а только когда
что-то изменилось (патч, прокси, превью-мазок, панорама), склеивая несколько
изменений в один rAF.

## 4. Бинарный формат точек мазка (клиент → TD)

Little-endian, заголовок 9 байт, затем `count` точек по 8 байт.

| Смещение | Тип | Поле |
|---|---|---|
| 0 | `u8` | op = `1` (точки мазка) |
| 1 | `u32` | `strokeId` (монотонно растёт на клиенте) |
| 5 | `u8` | flags: bit0 = начало мазка, bit1 = конец мазка, bit2 = отмена мазка |
| 6 | `u8` | `layerId` |
| 7 | `u16` | `count` (1..127) |
| 9 | `count × 8` | точки |

Точка (8 байт):

| Смещение | Тип | Поле |
|---|---|---|
| 0 | `u16` | `x` = round(nx × 65535), nx ∈ [0,1) |
| 2 | `u16` | `y` = round(ny × 65535) |
| 4 | `u8` | `pressure` 0..255 (мышь = 128) |
| 5 | `u8` | flags: bit0 = разрыв (начало нового сегмента, не соединять с предыдущей точкой) |
| 6 | `u16` | резерв, = 0 |

Правила:

- Отправлять пачкой **не чаще 60 раз в секунду**, но не по одному `pointermove`:
  собирать точки через `pointerrawupdate` / `getCoalescedEvents()`.
- При `flags` bit0 (начало) сервер начинает новый мазок; точки, пришедшие без
  начала (потеря пакета/переподключение), трактуются как продолжение.
- При `flags` bit2 (отмена) сервер выбрасывает мазок и восстанавливает состояние
  из снимка, сделанного перед мазком.
- `count` в пачке — 1..127. Чтобы донести флаги в момент `pointerup` при пустом
  буфере, клиент повторяет последнюю точку (дубль штампа не создаёт); сервер
  **обязан** принимать и пачку с `count = 0`, где важны только флаги, — иначе мазок
  рисуется, но никогда не завершается.
- `pointercancel` завершает мазок (bit1), отмена по `Esc` — это bit2.

## 5. Алгоритм мазка (обе стороны обязаны совпадать по смыслу)

- `spacing` — доля от размера кисти; штампы ставятся по длине пути каждые
  `max(1, size * spacing)` пикселей полотна (по расстоянию, **не по времени**).
- Путь между точками интерполируется **линейно**, давление — тоже линейно.
- Штамп: круг радиуса `size/2` с мягкостью:
  `inner = radius * mix(0, 0.98, hardness)`, `a = 1 - smoothstep(inner, radius, dist)`.
- Пиксель получает `a * flow * pressure` (для мыши без давления `pressure = 0.5`).
- **Давление в v1 меняет только плотность штампа, радиус — всегда `size/2`.** Так
  рисует веб-клиент, и сервер обязан совпадать, иначе превью на планшете
  расходится с TD. Если хочется «толще от нажатия» — это
  `PRESS_SIZE` в `paint_runtime.py` (0.0 = совпадает с клиентом).
- Режимы: `brush` — цвет поверх; `eraser` — вычитание альфы; `mask` — та же кисть,
  но результат используется как альфа источника.
- Клиентское превью **приблизительное** (может отличаться по стыкам штампов), это
  нормально: его всегда перекрывает патч сервера.
- Накопление в сервере идёт за кадр, пачкой штампов (`acc = acc + a*flow*(1-acc)`
  внутри кадра), поэтому при быстром движении мазок не «пятнится».

## 6. Undo / redo

- Хранит сервер. Глубина по умолчанию 24 шага.
- Перед началом мазка сервер снимает состояние региона, после мазка — кладёт в стек.
- `undo`/`redo` возвращаются клиенту как **обычный `patch`** восстановленной области,
  плюс сообщение `{"t":"history",...}` для кнопок.
- Клиент не ведёт свою историю пикселей, но может сбрасывать оверлей превью.

## 7. Ограничения и защита

- Максимум штампов на кадр: 128 (сервер нарезает длинный мазок на несколько кадров).
- Патчи — не чаще `patchHz` (30) раз в секунду на клиента; прямоугольники за
  интервал объединяются в один bbox.
- Если клиентов нет — сервер не кодирует PNG/JPEG вообще (нулевая цена простоя).
- Прокси видео — не чаще `proxyFps` (по умолчанию 2; 0 = только постер).
- Точки от неизвестного `strokeId` без начала — принимаются как продолжение.
- Мусорные/битые сообщения не должны ронять сервер: ошибка → `{"t":"error"}` в лог, соединение живёт.

## 8. Что считается «готово» для v1

- Открыть страницу с планшета, выбрать картинку или видео как источник.
- Кистью и ластиком рисовать по полотну, ощущая мгновенный отклик.
- Переключить слой Paint в режим маски — источник проявляется там, где нарисовано.
- Undo/redo минимум 24 шага, pan/zoom, палитра + HEX.
- Видео: на планшете постер или медленный живой прокси, на TD — полный fps.
